Use the project-type skeleton. Write in this order: name; one complete benefit
sentence; at most four truthful badges and language link; theme-aware hero and
caption; Quick start install block plus at most four first-use lines; one line
of requirements; three source-backed benefits; a three-step workflow; options
(up to five rows, linking reference); 3–5 FAQs and boundaries; contributing;
license. Put legal detail in details. Never put benefits before installation.
Use full sentences and short paragraphs. No emoji headings, file trees, empty
superlatives or named alternatives by default. Commands must be runnable as
printed. Keep the English body within brief.wordBudget and every paragraph
within three sentences. Map every benefit sentence to a fact ID in claims.json.
For agent skills follow installation with “Then tell your agent:” and quote a
real request. Mirror structure, commands and images in Chinese; localize images.

The hero shows coreAction's real input and output, never an install/check result
or this project's own README text. Preserve integrations and old H2 information
via the README, linked docs, or reasoned intentional deletion in the report.
Compatible tools are not competitors. Keep their actual names and boundaries.

If the hero shows scores, its immediate caption must explain the calculation in
one sentence (for example, Audit score = share of README checks passed). Keep
the explanation in every README language; a FAQ alone does not satisfy V10.

Choose the visual by what makes the product useful: source-linked artifacts use
hero-link, transformations use hero-code with the real input and output, and
terminal workflows use hero-terminal. Do not replace an explanatory visual with
a file listing just because the listing is easy to capture. Preserve the old
README's strongest concrete claim when the code supports it. In the caption,
name the demonstrated scope and what is not demonstrated. Put the first useful
request/example directly after installation so a stranger can actually try it.

For short non-writing CLIs, keep the real input/output example compact enough
that both installation AND the first useful command remain visible. Capture the
actual CLI entry point, not a demo wrapper that prints a synthetic transcript.
Use capture --input-file with hero-code for a short transformation; show the
hashed input beside actual stdout. compact:true omits repeated art headings and
captions. A file path only present in the repository needs an explicit note.

Preserve a useful original brand banner, direct tagline and concise navigation
when they help scanning. Do not flatten them into an anonymous H1. Use original
local assets with accurate alt/theme variants. Keep technical provenance in a
short factual caption; do not let it displace the reason to try the product.

When readers prefer a branded original, compare at a similar logo display size
before discarding that preference as superficial. For linked artifacts, separate
name, value and source badge; source swatches and a measured verification status
should remain visually distinct. Preserve verification claims only from real
saved checks. Source glyphs and decoration never substitute for provenance.

Retain concise original navigation when it helps readers explore before installing.
For dense source lines, use the template's explicit single-line excerpts; preserve
full source files and all citation checks. A cluttered preview is not stronger
proof. Keep ellipses visible and make the recorded run/full source reachable.

Preserve truthful existing status badges (CI, version, license and runtime) by
default, directly below the one-sentence introduction. Account for every badge
from baseline.json: retain its image and destination, or record its stable ID
and a specific reason in docs/readme/retention.json intentionalDeletions (e.g.
the status endpoint is dead or the claim is false). Removing badges for visual
simplicity is not the default. V11 fails unaccounted badge deletions.
